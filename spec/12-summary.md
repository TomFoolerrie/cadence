# Summary

| Concept | Rule |
|---------|------|
| Who owns the hierarchy | The user. It's folders on their computer. Local-only in MVP. |
| Three levels | Root (context) → Class (orchestration) → Task (execution). |
| Where the user lives | The task level. That's where work happens. |
| Root | `.context-root` (YAML file with `engagement` and `schema_version` fields) + `AGENT.md` — entity context loaded into every session. Uses the same filename as class-level context for consistency. |
| Class | `.class.yaml` (orchestration manifest — tasks and phase order) + `AGENT.md` (class context for task agents). Class status is computed on the fly by `/status` from task `status.yaml` files. |
| Task | `SKILL.md` + `learned.md` + `status.yaml` + `tools/` + `periods/`. Self-contained work folder. |
| Status | Six states: `not_started`, `in_progress`, `review_ready`, `blocked`, `done`, `abandoned`. `status.yaml` tracks period and execution state. `done` and `abandoned` are terminal. `review_ready` means draft is ready for human/orchestrator review. `blocked` requires human intervention (retry or abandon). `in_progress → in_progress` is idempotent (crash recovery). `review_ready → in_progress` allows draft rejection and re-execution. |
| Context inheritance | `load-context.py --level <level>` loads context top-down (pure, no side effects). Loads root/AGENT.md → class/AGENT.md → task files. Class agents get `AGENT.md` (not `.class.yaml`). `--orchestrator` flag loads `.class.yaml` manifest. Level is always declared by the caller, never detected. Includes recovery hints for blocked tasks. |
| Tool inheritance | Three tiers: global → class → task. Resolution: task > class > global (most specific wins). Common logic lives at the highest appropriate level. |
| Task lifecycle | `/onboard` from root creates a class (`init-class.py`); `/onboard` from class creates a task (interview, first period execution to `review_ready`). SKILL.md includes a Completion Criteria section populated during `/onboard`. `/done` completes the first period (same conversation as `/onboard`). `/start` + `/done` for recurring execution + review, starting from second period. `/done` always runs in the same conversation as the preceding `/start` or `/onboard`. `/status` for class progress dashboard. Fresh agent per execution. |
| Error protocol | Task: `not_started → in_progress → review_ready → done` (happy path). `/start` sets `in_progress` then `review_ready`; `/done` sets `done` after review (auto-writes `done_at` timestamp). `blocked` for failures — human retries or abandons via `/start`. `review_ready → in_progress` for rejected drafts (via `/start`). `abandoned` for unrecoverable issues. Class status derived from tasks — `done` when all enabled tasks are `done` or `abandoned`. |
| Orchestration (phases) | Order-based. All phase N tasks must complete before any phase N+1 task starts. No cross-task dependencies beyond phase ordering. |
| Prior-period guard | `init-period.py` checks that status is `in_progress` before creating a period directory. `/start` sets `in_progress` first, then calls `init-period.py`. This ensures the task is actively being worked before scaffolding a new period. |
| Period string convention | The period string refers to the **period being closed**, not the current calendar period. E.g., period `2026-03` is worked on in April. |
| Folder is the memory | The agent is stateless. Everything persists in the folder. A fresh instance can execute any task. |
| Orchestration (future) | An orchestrator uses `load-context.py --level class --orchestrator`, reads `.class.yaml`, launches sub-agents per phase, reviews their output. Serializes class-level state writes. |
| Git versioning | Every structural change committed automatically. Procedures, learnings, review notes, and status tracked. Source data and workpapers excluded. |
| Workpapers | Not git-tracked. Generated outputs that can be reproduced. Future Drive feature archives them off-disk when period completes. |
| Portability | The hierarchy is a standalone artifact. Any runtime that reads markdown/YAML can execute it. No plugin required. |
| File authority | `learned.md` is self-managed by the agent (counters are optional metadata; agent consolidates when the file gets long). `SKILL.md` changes proposed in Cowork conversation — human approves verbally (unenforced convention in MVP; orchestrator enforces in future). |
| Hierarchy depth | Exactly three levels: root → class → task. No nesting beyond this. `load-context.py` relies on this structure. |
| Only Claude writes | Agent-initiated state modifications flow through `set-status.py` (agent/skill gateway). `check-periods.py` is the only non-agent writer (infrastructure scheduler, runs as cron at 6am). Class status is computed on the fly by `/status` from task `status.yaml` files — not persisted. Hand-edits to `SKILL.md`/`learned.md` are safe. Developer escape hatch exists for all files. Source data provided by human via Cowork UI. |
| Agent write scope | Task agents are write-scoped to their task folder with read access to the entire hierarchy. Scripts invoked by the agent can write wherever their contracts specify. `/onboard` (task-level) has class-level write scope for manifest updates. Agents must never directly edit `status.yaml` or `.class.yaml`. Configured on the agent, not enforced by filesystem. |
| Period format | Configurable per task via `period_format` in `.class.yaml`. Values: `monthly` (`YYYY-MM`, default), `weekly` (`YYYY-WNN`), `quarterly` (`YYYY-QN`), `adhoc` (user-defined slug). Different tasks within a class can use different period formats. |
| Anchor (scheduling) | Day-of-week anchor for when a task triggers. Default: `first_monday`. Values: `first_monday`..`first_friday`, `last_monday`..`last_friday`, `monday`..`sunday`. Advisory in MVP (human reads it as a reminder), machine-readable in future state. Set during `/onboard`. |
| Period advancement | `check-periods.py` is a scheduled infrastructure script (cron, early morning) that automatically resets terminal tasks when their next anchor date arrives. Writes `status.yaml` directly (not through `set-status.py`). Reads `done_at` + `anchor` + `period_format` per task. Each task evaluated independently — mixed frequencies work naturally. `adhoc` tasks excluded (require manual `/start`). |
| Git commits | Skills own git commits (scripts have no git side effects). Atomic per skill invocation. On partial failure, no commit — human inspects intermediate state. |
| Script separation | `load-context.py` is pure context assembly (no side effects). `set-status.py` is the agent/skill gateway for `status.yaml` (validates transitions, auto-writes `done_at` on terminal states). `check-periods.py` is the infrastructure scheduler (writes `status.yaml` directly for period resets). `init-period.py` is pure scaffolding (checks `in_progress` guard, no status writes). `init-class.py`, `init-task.py` are scaffolding scripts. `archive-period.py` uploads completed period data to Google Drive after `/done` commit. `install-deps.py` targets Cowork VM only. Skills compose the scripts they need (see Section 5.2.3). |
| State management | Two authorized `status.yaml` writers: `set-status.py` (agent/skill gateway — validates transitions, rejects invalid ones) and `check-periods.py` (infrastructure scheduler — resets terminal tasks for new periods). No class-level state file — class status is computed on the fly by `/status`. |
| `/done` constraint | `/done` always runs in the same conversation as the preceding `/start` or `/onboard`. It does not load context independently — the active conversation provides all context. Not a standalone skill. `/done` handles all period completion: learnings capture, `done` status, git commit, and Google Drive archival — including the first period after `/onboard`. |
| Script failure contracts | All scripts use exit codes: 0 (success), 1 (validation error — e.g., invalid transition, missing prerequisite), 2 (system error — e.g., couldn't write file). Side-effect guarantee: if a script exits non-zero, no partial state is written. Scripts are idempotent where possible. |
| Period archival | `archive-period.py` is called by `/done` after the git commit. Uploads the completed period's `workpapers/` and `data/` to Google Drive, mirroring the hierarchy structure. |
| Plugin relationship | Plugin provides skills (/onboard, /start, /done, /status) and scripts. Hierarchy provides structured context. Stored separately. Known limitation: `requirements.txt` at multiple levels may have version conflicts. |
