# Ticket 01: Runtime-portability decouple — un-pin Cadence from Claude Code

**Status:** TODO
**Repo:** cadence
**Depends on:** 00
**Source of truth:** `00-integration-design.md` (the mapping table), `spec/06-separation-of-concerns.md`.

## Goal

Make Cadence's executable layer (scripts + the things a skill tells the agent to do) run under **any**
runtime that has Python + bash + git, not just Claude Code — without changing behaviour under Claude
Code. This is the prerequisite that lets Pi drive Cadence (Tickets 02, 03) and keeps Cadence's
Cowork/Claude-Code path working unchanged.

## Background — exactly what is Claude-Code-coupled today

A pass over `plugin/skills/*/SKILL.md` and `plugin/scripts/*.py`:

1. **`${CLAUDE_PLUGIN_ROOT}`** — every skill invokes scripts as `python ${CLAUDE_PLUGIN_ROOT}/scripts/<x>.py`.
   This env var is set by the Claude Code plugin loader. Under Pi it does not exist.
2. **Skills are prompt injections, not files Pi reads.** `/start` etc. only exist as slash commands in
   Claude Code. (Ticket 03 handles the translation; this ticket only ensures the *scripts* they call
   are reachable runtime-agnostically.)
3. **`.claude/settings.json` write-scope** — generated by `init-*.py`. A Claude Code construct; Pi
   ignores it. (Ticket 04 replaces the enforcement; this ticket decides whether the init scripts
   should still emit it — yes, keep emitting for the Cowork path; it's inert under Pi.)
4. **cwd assumptions** — open-item #18: skills assume cwd is the class/task dir. A headless run sets
   cwd = engagement root and selects the task explicitly.

## Work items

- [ ] **Parametrize the plugin root.** Introduce `CADENCE_PLUGIN_ROOT` as the canonical var; have the
      scripts/skills resolve the plugin root as `CADENCE_PLUGIN_ROOT` → fall back to `CLAUDE_PLUGIN_ROOT`
      → fall back to a path derived from the script's own `__file__`. The `__file__` fallback makes a
      bare `python plugin/scripts/set-status.py` work with no env at all (best for headless + tests).
- [ ] **Confirm task selection from engagement root.** A headless run needs to operate on a named task
      without `cd`-ing interactively. Decide the mechanism: a `CADENCE_TASK=<class>/<task>` (relative to
      the engagement root) consumed by the method-pin (Ticket 03), and verify the scripts' walk-up
      helpers (`.absolute()`-based, per open-item #17) resolve correctly when cwd is the task dir under
      `/work`. No script change expected here — just a documented contract + a test.
- [ ] **Keep `.claude/settings.json` emission.** `init-*.py` continue to write it (Cowork path needs
      it; it is inert and harmless under Pi). Document that under Pi the *equivalent* enforcement is the
      gate (Ticket 04), and that the deny rules in those files are the **spec** Ticket 04 must mirror.
- [ ] **No behavioural change under Claude Code.** Existing 299 tests must still pass. Add tests for
      the new resolution order (`CADENCE_PLUGIN_ROOT` set / unset / `__file__` fallback).

## Acceptance

- `python plugin/scripts/set-status.py review_ready` (and the other gated scripts) run correctly from a
  task dir with **no** `CLAUDE_PLUGIN_ROOT` and **no** `CADENCE_PLUGIN_ROOT` set (the `__file__`
  fallback), and identically when `CADENCE_PLUGIN_ROOT` points at `plugin/`.
- `python -m pytest tests/` stays green (≥299), plus new resolution-order tests.
- This ticket's "exactly what is coupled" list is confirmed exhaustive by a fresh grep, recorded here.

## Notes / risks

- This is deliberately a *thin* ticket: the bet is Cadence is already ~90% runtime-agnostic. If the
  grep surfaces deeper coupling (e.g., a script importing a Claude-Code-only module), surface it here
  and re-scope — do **not** quietly fork a script.
